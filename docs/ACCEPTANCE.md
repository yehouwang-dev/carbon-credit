## 评测方式与边界

先采用“输入 → 预期行为 → 实际行为 → 通过/失败 → 原因”的基本评测思路，不引入或部署 Scope。

测试从现有 `App.jsx` 提取实际查询函数，注入模拟合约接口和状态记录函数。它不是复制一份业务逻辑再测试自己的副本。接口依次返回预设记录、不存在错误、挂起请求和网络错误；所有数据都是虚构测试数据。

这属于**函数级验收与故障注入**，不是完整网页端到端测试，不代表 Sepolia 合约已部署或真实交易已验证。不会连接钱包、调用真实 RPC、广播交易或使用私钥。界面文案使用翻译键作为断言，因此未验证翻译、视觉布局或辅助功能。

### A03：超时的证据和解释

现有函数直接等待 `contracts.CarbonCredit.getRetirement(...)`，函数本身没有超时截止或取消机制。在来源永不完成的故障模型下，调用持续挂起。

测试里的 **250ms 是缩短的观察窗口，不是生产服务应遵循的响应时限**。观察后由测试主动拒绝模拟请求，避免测试自身悬挂；这一步不是应用已经实现的超时处理。当前结果还结合了函数内没有截止机制的代码检查。真实 RPC/ethers 提供方可能有自己的超时，但本次测试没有验证它们，也不能据此声称真实网页一定会永久挂起。

### A05：“无结果”和“来源不足”不同

- 无结果：来源可用，明确告诉我们该 ID 不存在。
- 来源不足：来源不可达，无法判断 ID 是否存在。

目前 `catch` 把所有异常统一显示为 `certificateNotFound`，因此混淆了这两类情况。这里的“来源”特指合约/RPC 查询来源；本次没有评测文献引用或语言模型回答的来源充分性。

从仓库根目录运行：

```bash

```

测试文件：`fronted/test/acceptance.test.js`。依赖已有 ethers，不需要新增测试框架。未安装依赖时，先执行 `npm --prefix fronted ci`。

## 基础概念

- **验收标准**：先写清楚怎样才算符合要求，再看结果。
- **断言**：用程序检查“返回数量是否为 10”“是否完全没有调用接口”等条件。
- **模拟接口（Mock）**：用可控返回值或故障替代真实服务，稳定复现问题；不等于真实服务已验证。
